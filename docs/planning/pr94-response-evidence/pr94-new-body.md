## Background

`methodology_trim.py` trims a **ledger**: a file of dated records, newest first, that grows with every session. The trimmer works only on the ledgers listed in its **ledger table**, a Python dictionary named `LEDGERS` that is written in the code of `methodology_trim.py` (there is no separate configuration file). The table has two entries: `CHANGELOG.md` (one record per action) and `HANDOFFS.md` (one record per session, called a receipt). When it trims, the trimmer refuses a file that has no table entry (exit 3). This repository is the framework's own; `bin/sync` copies `methodology_trim.py` from it into the projects that use the framework (*adopters*).

A trim moves the oldest records of a ledger into an archive file, a **shard** (in `docs/archive/`), and writes a **proof** next to it, in the same directory: `<shard>.verify.sh`. The commit that adds the shard is the **trim commit**. The trimmer writes a short header at the top of the shard; the header says which ledger the records came from and how many records the shard holds. The trimmer generates each proof from a template (`VERIFY_TEMPLATE`). The proof is a script that re-checks, from git, that the trim lost nothing: it compares the ledger as it was in the trim commit's parent (*before*) with the ledger and the shard as they are in the trim commit (*after*). The proof runs three checks:

- **L1:** every byte of the *before* ledger's records is still in the *after* ledger's records or in the shard's records.
- **L2:** the ledger's header (the text above the first record, which the trimmer calls *front matter*) and footer (the text below the last record; `HANDOFFS.md` has none) are still in the ledger, and no line of them was copied into the shard (neither into the shard's own header nor among its records). Two exceptions: the header fields that the trimmer, not the session, rewrites (such as a receipt count) may change, and header lines of 24 characters or fewer are not checked for copying.
- **L3:** each record of the *before* ledger is, unchanged and in order, either in the *after* ledger or in the shard. Records that the trim commit itself added to the ledger (a new session's records, for example) are left out of the comparison.

A proof exits 0 when the checks hold and 1 when one fails. A proof is written once, when the trim happens, and never changes afterwards (it is *frozen*). Each proof states the trimmer version that wrote it; the trimmer's version number is `TRIM_VERSION`.

## What issue #93 reports

Issue #93 reports 10 of the 54 proofs in one adopter repository, `rmsharp/nprcgenekeepr` (the *#93 repository*), failing. The authors of #93 diffed the records of all 10 by hand and found no real loss, so each is a *false FAIL*: a FAIL on a trim that lost nothing. The issue traces the 10 to three causes.

The #93 repository also trims a third ledger, `SESSION_NOTES.md` (a file with one record per session's write-up, plus one for each evaluation of the previous session's handoff). Because the trimmer refuses a file with no table entry, the repository added a table entry for it to the `LEDGERS` table in its own copy of `methodology_trim.py`. The table in this repository's `methodology_trim.py` has no such entry; the `SESSION_NOTES.md` pull request adds it.

1. **A trim in the same commit as a finalize (7 proofs).** A session starts by committing a placeholder record at the top of a ledger, the *stub*; that commit is the session's *claim*. In `HANDOFFS.md` the stub is a receipt marked `status: pending`; in `SESSION_NOTES.md` it is a record whose first line is `**Deliverable:** ... (IN PROGRESS)` and which carries the line `**Status:** Session claimed. Work beginning.` (the session runner's Phase 1B writes both). The session ends by overwriting the stub in place with the finished record: the *finalize*. When a trim lands in the same commit as the finalize, the proof sees the newest record (*record 0*, which the trimmer also calls the *frontier*) change. The proof prints record 0 as `MISSING:` and prints an added record with the same identifying line (its heading, or the `session:` line of a receipt) as `added:`; that is the *finalize pattern*. The proof fails L1 and L3.
2. **L2 compares by substring (2 proofs).** L2 treated a line of the ledger's header as copied into the shard whenever the line occurred anywhere inside an archived record. A record that quoted the header line `## Size, and when to archive` in backticks, inside a longer line, therefore counted as a copy.
3. **A proof already written never gets later fixes (1 proof).** The template has been fixed since, but a proof is never regenerated. The cause-3 proof was written by trimmer version 1.1.2, whose template assumed that the trim commit adds a fixed number of records to the ledger, written into each proof as a constant (`INJECTED=0`: assume none). The trim commit also contained the session's close-out (the step that finishes a session). The close-out added one new record, an evaluation of the previous session's handoff, and overwrote the stub. The ledger and the shard together then held one record more than before the trim, 79 against 78, so L3 reported `record count 79 != 78`. Version 1.2.0 replaced the constant with a measurement of which records the trim commit added, but this proof was not regenerated.

**Commit 1 (`TRIM_VERSION` 1.5.1): L2 compares whole lines. Fixes cause 2.** L2 now tests whether a line of the ledger's header equals a whole line of the shard's header or of its records, instead of occurring anywhere inside them. The 24-character exception stays.

**Commit 2 (`TRIM_VERSION` 1.6.0): a stub finalize is recognised and warned about. Addresses cause 1.** The *timing rule* avoids the problem: give the trim a commit of its own, never in the same commit that edits record 0. (This commit worded the rule as "trim while record 0 is complete, that is, before the claim or after the finalize is committed", which is stronger than the proof enforces; Commit 13 replaces that with the wording above. See "Changes since the first review" for what Commits 8 and 13 are.) This commit adds three things:
- **A proof that recognises a stub finalize.** An entry in the ledger table can declare a `stub_marker`: a regular expression that identifies a pending stub (for `HANDOFFS.md`, the whole line `status: pending`, so a receipt that merely quotes the marker inside a longer line is not taken for a stub; Commit 8 narrows this further, to a line inside the receipt's own fence). A proof is a self-contained script that does not import the trimmer, so it cannot look the marker up; it contains a copy as `STUB_PATTERN`. When record 0 matched the stub marker before the trim, no longer matches it after, L2 holds, and every other record is unchanged and in order, the proof recognises a *stub finalize*. It prints one specific `FAIL:` line (for example `FAIL: record 0 was a pending stub (606 B) and was finalized in the trim commit; the other 5 record(s) are byte-identical across the move, in order, and L2 holds`) and a `NOTE:` line, and exits 4, in place of the generic L1 and L3 failures. Exit 4 is still a FAIL, by design (see "What remains"). The `NOTE:` line explains why exit 4 is still a FAIL and states the timing rule.
- **A warning before the write.** Before it writes, the trimmer prints a warning coded `FRONTIER_PENDING_STUB` (record 0 is a pending stub now) or `FRONTIER_FINALIZE_UNCOMMITTED` (the last commit's record 0 was a pending stub and the working tree no longer holds it: the finalize is made but not committed). The warnings are advisory and refuse nothing.
- **The rule, stated.** The warnings, the proof's `NOTE:` line and `FRAMEWORK_APPARATUS.md` state the timing rule. A proof that does not recognise a stub finalize already printed a `NOTE:` line when it met the finalize pattern; this commit rewords that line to state the timing rule. The old wording had called committing a finalize together with a trim this repository's own practice; the new wording says it is not the framework's practice.

**Commit 3 (`TRIM_VERSION` 1.7.0): a second verdict for a proof already written. Addresses cause 3.** To *re-derive* a shard's proof is to build the proof that the *running trimmer* would write for that shard, from its own template, and run it. The running trimmer is the version of `methodology_trim.py` that is executing `--reverify`, as against the version recorded in the shard's original proof. `methodology_trim.py --reverify <shard>` (the shard, or its `.verify.sh`) does that, as follows. Unlike a trim, `--reverify` needs no table entry for the ledger.
- `--reverify` reads from the shard's existing proof the ledger's path (`LIVE`), the shard's path (`SHARD`), and the *record grammar*, which says how records are told apart: `RECORD_KIND` (records are dated headings or fenced blocks), `RECORD_START` (a regular expression that matches the line that begins a heading record), `FENCE_INFO` (the word after a fenced record's opening fence, such as `handoff`) and `FOOTER_MODE` (whether the ledger has a footer). When the proof has them, `--reverify` also reads `REGEN_PATTERNS` (regular expressions that find the header fields the trimmer, not the session, rewrites) and `STUB_PATTERN`.
- `--reverify` fills in a value that the existing proof lacks. A proof written before 1.6.0 has no `STUB_PATTERN`; `--reverify` uses the `stub_marker` of the ledger table's entry for the ledger's file name, or none if the table has no entry or the entry declares no `stub_marker` (the `CHANGELOG.md` entry declares none). A proof written before 1.1.2 has no `REGEN_PATTERNS`; `--reverify` uses none, so no header field is exempted. The banner says which values were filled in.
- `--reverify` prints a banner first, saying that the verdict comes from the running trimmer's logic and not from the original proof file, and a line for each value it substituted. It then runs the re-derived proof and prints the proof's own output as the verdict.
- The exit status is that of the re-derived proof (0 holds, 1 FAIL, 4 stub finalize), or 3 when no verdict can be reached: the shard is outside a git work tree, has no proof next to it, its proof is for a different shard or has a line that is not in the exact form the template writes, or the re-derived proof cannot be run to the end.

`--reverify` writes no file: it passes the re-derived proof to `bash -c`, so the shard, the original proof and git are unchanged. The original proof stays as it was, so there are two verdicts on the shard: the original proof's, whenever it is run, and the one `--reverify` prints. A proof written by this branch's trimmer and a proof re-derived by `--reverify` come from the same function (`render_verify`), so they behave alike.

**Commit 4 (`TRIM_VERSION` 1.8.0): the proof prints the record-0 diff.** Whenever the proof sees the finalize pattern (record 0 edited in the trim commit, for a recognised stub finalize at exit 4 and for the generic case at exit 1 alike), it prints, after its `FAIL:` and `NOTE:` lines, a unified diff of record 0 before the trim commit against the record that replaced it, headed `DIFF: record 0, ...` with the line count. This is issue #93's first suggestion. The diff is output, not a verdict: it changes no exit status, and a record other than record 0 that differs gets no diff, because that is a plain loss (Commit 11 also withholds the diff, and says so in a note, when record 0 was edited and other records moved as well). Three tests; 7 mutants of the printing code (never printed, printed for any missing record, printed only for the recognised case, reversed, header dropped, lines dropped, the wrong record compared) are all caught. Minor version bump: new proof output, no verdict changes.

**Commit 5 (`TRIM_VERSION` 1.8.1): an abort before the proof's checks exits 3, not 1.** A proof that cannot read an artifact from git (a partial or shallow clone that lacks the trim commit's parent; a blob fetch that fails) ended in `sys.exit("verify: cannot read ...")`, which exits 1, the FAIL code, so a proof that had compared nothing read as a trim that lost something; a run of `--reverify` over all 54 shards of the #93 repository (see Evidence) saw it once (exit 0 on the re-run). Every such abort now prints its reason and exits 3, the code the `--reverify` legend gives "the proof did not finish". Frozen proofs are unchanged; `--reverify` renders today's template and reads 3. Four tests on a depth-1 clone of a trimmed repository; the `trimmer-unit-tests` gate 184 → 188; the 54 proofs read the same under 1.8.1 as under 1.8.0. (Commit 6, in the table below, refines which aborts are exit 3: a path missing from a commit the clone can read is a FAIL.)

## Where to read closely

`--reverify` reads values out of a proof file that belongs to the repository being checked, so the file's text is not trusted. `--reverify` places some of the values into an unquoted shell assignment and the rest into Python, in the proof that it then runs, so a value containing shell or Python code would run. The reading is therefore strict, not a loose pattern match:
- each required line must match, whole, the form the template writes;
- `REGEN_PATTERNS` and `STUB_PATTERN` are parsed as literals and never evaluated;
- paths may not be absolute or contain `..`.

The code is in `starter-kit/methodology_trim.py`. "Lift" is the code's word for reading a value out of a proof: `_LIFT_REQUIRED` lists the lines that must be present and the exact form of each, `_lift_line` finds one such line, `_lift_pattern` checks a pattern value, and `lift_grammar` does the whole reading. Four tests plant hostile text: (1) shell code in the `LIVE` line; (2) Python code in the `RECORD_START` line; (3) a Python expression in the `REGEN_PATTERNS` line, and then in the `STUB_PATTERN` line (one test, run for each line); (4) a shell command in a shard's file name. Each test has a control showing the text would run if pasted in naively, then asserts that `--reverify` refuses it and nothing runs.

`--reverify` now also refuses, by name and at exit 3, a frozen proof whose `PREFIX` line is missing, repeated, not in the form the template writes, or not `"../../"` (Commit 9), and one whose `RECORD_START` line carries a carriage return or a NUL (Commit 10). Each has tests that build the hostile proof and assert the refusal.

`HANDOFFS.md`'s stub marker is, since Commit 8, this regular expression under `re.M`:

```
\A(`{3,}|~{3,})handoff[^\n]*\n(?:(?!\1)[^\n]*\n)*?status: pending[ \t\r]*$
```

The line must be inside the fence that opens the record, which ends at a line starting with the same run of backticks or tildes that opened it. It is a lazy line-by-line scan, linear in the record; a test searches a 400,000-line record that has no marker. The diff is built with Python's `difflib` from the two record texts the proof already holds.

## What remains, and why the named ones stay FAILs

The authors of #93 ask for these false FAILs to stop. The original proof files do not change, so for a proof already written this PR can only add a second verdict, the one `--reverify` gives. Under that verdict, 2 of the 10 proofs pass and 1 is recognised as a stub finalize: a specific `FAIL:` line, exit 4, and the diff of the stub against the record that replaced it. With the `SESSION_NOTES.md` pull request applied, in each of the 8 the re-derived proof reports the finalize pattern: record 0 was a stub before the trim commit, a record with the same heading or `session:` line replaced it, and no other record differs. The cause-3 proof shows the same pattern, because its trim commit overwrote the stub as well as adding a record. The pattern stays a FAIL by design, because neither the original proof nor the re-derived one can tell it from a real loss: if the edit to record 0 had also deleted part of its text, the proof would see the same pattern, record 0 changed and everything else identical. In all 8 the finished record rewrote the stub's text; apart from the identifying lines, no line of the stub survives as a whole line in the finished record, and one stub carried 23 lines of prose written into it. #93's authors judged by hand that nothing of value was lost; a proof cannot, and a proof that exited 0 here would certify a replaced stub it has not read. What the proof can do is show the edit, which is what the diff is for: in these 8 the diff runs from 30 to 176 lines (all 8 print it with this PR alone), and a reader sees in seconds that the removed lines are the placeholder's and the added lines are the session's write-up.

Commits 1, 2, 4, 5 and 6 to 14 change only what a *new* trim writes and warns about and what a new or re-derived proof prints, refuses or exits with; commit 3 adds a flag. Nothing rewrites a proof already in an adopter's `docs/archive/` directory.
- **Exit codes are more specific, measured against 1.5.0 (what adopters hold).** A proof that cannot read a commit, tree or blob from git now exits 3 (it exited 1; Commit 5). A proof whose history walk fails now exits 3 (it printed `OK`; Commit 14). A path absent from something the proof can read still exits 1 (Commit 6 restores 1.5.0's answer after Commit 5 moved it to 3). `--reverify` refuses more frozen proofs, at exit 3, by name: a `PREFIX` other than `"../../"`, a carriage return or a NUL in `RECORD_START`. A caller that treated 3 as "could not run" is unaffected.
- **Exit status 4 is new** for a generated proof. A caller that tests `== 1` rather than `!= 0` would miss exit 4. Nothing in this repository calls a proof that way (outside `docs/archive/`, the tests and the trimmer, `verify.sh` appears only in prose and a hook comment); an adopter's own script might.
- **A proof's output grows** when record 0 was edited in the trim commit and no other record moved: the diff is printed after the `FAIL:` and `NOTE:` lines, 30 to 176 lines in the 8 shards of the #93 repository. A proof whose checks hold prints nothing new.
- **The timing rule's wording changes** (in the trimmer's warnings, the proof's notes and `FRAMEWORK_APPARATUS.md`): "give the trim a commit of its own, never in the same commit that edits record 0". It no longer tells a session to wait for a complete record 0.
- **`SESSION_NOTES.md` is not in the table in this PR.** A project that carries its own table entry for it (the #93 repository does) is unaffected only while it does not sync: `bin/sync` stops on its locally edited `methodology_trim.py` (exit 2, naming the file), and with `--force` it overwrites the copy and removes the local entry, so that project cannot trim `SESSION_NOTES.md` again until the `SESSION_NOTES.md` pull request lands. This PR does not change how `bin/sync` treats a locally edited file.
- The dashboard (`methodology_dashboard.py`) reads `TRIM_VERSION` with a regex, and the regex still matches.
- A newly generated proof differs from an older one in its text as well as its behaviour: new comments, one reworded comment (it no longer calls committing a finalize together with a trim this repository's practice), the reworded `NOTE:` lines, and the interpreter line `python3 -I -`.

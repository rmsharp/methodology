## Summary

This PR changes `methodology_trim.py` (the trimmer), the tool that moves the oldest records out of a growing file into an archive file and writes a script, a *proof*, that re-checks that nothing was lost. Issue #93 reports 10 of 54 proofs, in one project, failing on trims that lost nothing, and traces them to three causes. This PR has four commits. The first fixes one cause (2 of the 10 proofs). The second teaches the proof to recognise the shape behind the other 8, a trim committed together with the finishing of a session's placeholder record, and to name it instead of printing generic failures. The third adds a command, `methodology_trim.py --reverify <shard>` (a *shard* is an archive file that an earlier trim wrote), that builds a new proof for a shard from the current template and runs it, so a shard whose proof was written earlier gets a second verdict. The fourth adds the project's third ledger, `SESSION_NOTES.md`, to the trimmer's table, so that the recognition reaches the 7 of those 8 that are shards of that file, and makes the proof print the diff of the placeholder against the record that replaced it.

Under `--reverify`, 46 of the 54 proofs pass and the other 8 are each named as a stub finalize and exit 4 with that diff printed; none prints the generic failures any more. The 8 stay FAILs by design, for the reason "What remains" explains. Whether a named FAIL with its diff answers the report is for issue #93's author; this PR does not close the issue.

## Background

`methodology_trim.py` trims a **ledger**: a file of dated records, newest first, that grows with every session. The trimmer works only on the ledgers listed in its **ledger table**, a Python dictionary named `LEDGERS` that is written in the code of `methodology_trim.py` (there is no separate configuration file). Before this PR the table had two entries: `CHANGELOG.md` (one record per action) and `HANDOFFS.md` (one record per session, called a receipt). The fourth commit adds a third, `SESSION_NOTES.md` (one or two records per session; see Commit 4). When it trims, the trimmer refuses a file that has no table entry (exit 3). This repository is the framework's own; `bin/sync` copies `methodology_trim.py` from it into the projects that use the framework (*adopters*).

A trim moves the oldest records of a ledger into an archive file, a **shard** (in `docs/archive/`), and writes a **proof** next to it, in the same directory: `<shard>.verify.sh`. The commit that adds the shard is the **trim commit**. The trimmer writes a short header at the top of the shard; the header says which ledger the records came from and how many records the shard holds. The trimmer generates each proof from a template (`VERIFY_TEMPLATE`). The proof is a script that re-checks, from git, that the trim lost nothing: it compares the ledger as it was in the trim commit's parent (*before*) with the ledger and the shard as they are in the trim commit (*after*). The proof runs three checks:

- **L1:** every byte of the *before* ledger's records is still in the *after* ledger's records or in the shard's records.
- **L2:** the ledger's header (the text above the first record, which the trimmer calls *front matter*) and footer (the text below the last record; `HANDOFFS.md` and `SESSION_NOTES.md` have none) are still in the ledger, and no line of them was copied into the shard (neither into the shard's own header nor among its records). Two exceptions: the header fields that the trimmer, not the session, rewrites (such as a receipt count) may change, and header lines of 24 characters or fewer are not checked for copying.
- **L3:** each record of the *before* ledger is, unchanged and in order, either in the *after* ledger or in the shard. Records that the trim commit itself added to the ledger (a new session's records, for example) are left out of the comparison.

A proof exits 0 when the checks hold and 1 when one fails. A proof is written once, when the trim happens, and never changes afterwards (it is *frozen*). Each proof states the trimmer version that wrote it; the trimmer's version number is `TRIM_VERSION`.

## What issue #93 reports

Issue #93 reports 10 of the 54 proofs in one adopter repository, `rmsharp/nprcgenekeepr` (the *#93 repository*), failing. The authors of #93 diffed the records of all 10 by hand and found no real loss, so each is a *false FAIL*: a FAIL on a trim that lost nothing. The issue traces the 10 to three causes.

The #93 repository also trims a third ledger, `SESSION_NOTES.md` (a file with one record per session's write-up, plus one for each evaluation of the previous session's handoff). Because the trimmer refuses a file with no table entry, the repository added a table entry for it to the `LEDGERS` table in its own copy of `methodology_trim.py`. The table in this repository's `methodology_trim.py` had no such entry before this PR's fourth commit.

1. **A trim in the same commit as a finalize (7 proofs).** A session starts by committing a placeholder record at the top of a ledger, the *stub*; that commit is the session's *claim*. In `HANDOFFS.md` the stub is a receipt marked `status: pending`; in `SESSION_NOTES.md` it is a record whose first line is `**Deliverable:** ... (IN PROGRESS)` and which carries the line `**Status:** Session claimed. Work beginning.` (the session runner's Phase 1B writes both). The session ends by overwriting the stub in place with the finished record: the *finalize*. When a trim lands in the same commit as the finalize, the proof sees the newest record (*record 0*, which the trimmer also calls the *frontier*) change. The proof prints record 0 as `MISSING:` and prints an added record with the same identifying line (its heading, or the `session:` line of a receipt) as `added:`; that is the *finalize pattern*. The proof fails L1 and L3.
2. **L2 compares by substring (2 proofs).** L2 treated a line of the ledger's header as copied into the shard whenever the line occurred anywhere inside an archived record. A record that quoted the header line `## Size, and when to archive` in backticks, inside a longer line, therefore counted as a copy.
3. **A proof already written never gets later fixes (1 proof).** The template has been fixed since, but a proof is never regenerated. The cause-3 proof was written by trimmer version 1.1.2, whose template assumed that the trim commit adds a fixed number of records to the ledger, written into each proof as a constant (`INJECTED=0`: assume none). The trim commit also contained the session's close-out (the step that finishes a session). The close-out added one new record, an evaluation of the previous session's handoff, and overwrote the stub. The ledger and the shard together then held one record more than before the trim, 79 against 78, so L3 reported `record count 79 != 78`. Version 1.2.0 replaced the constant with a measurement of which records the trim commit added, but this proof was not regenerated.

## What this PR changes

One commit per change, each with its own tests and its own record in `CHANGELOG.md`. The four share the proof template and its tests, so they are one change set.

**Commit 1 (`TRIM_VERSION` 1.5.1): L2 compares whole lines. Fixes cause 2.** L2 now tests whether a line of the ledger's header equals a whole line of the shard's header or of its records, instead of occurring anywhere inside them. The 24-character exception stays.

**Commit 2 (`TRIM_VERSION` 1.6.0): a stub finalize is recognised and warned about. Addresses cause 1.** The *timing rule* avoids the problem: trim while record 0 is complete, that is, before the claim or after the finalize is committed, never in the same commit as the finalize. This commit adds three things:
- **A proof that recognises a stub finalize.** An entry in the ledger table can declare a `stub_marker`: a regular expression that identifies a pending stub (for `HANDOFFS.md`, the whole line `status: pending`, so a receipt that merely quotes the marker inside a longer line is not taken for a stub). A proof is a self-contained script that does not import the trimmer, so it cannot look the marker up; it contains a copy as `STUB_PATTERN`. When record 0 matched the stub marker before the trim, no longer matches it after, L2 holds, and every other record is unchanged and in order, the proof recognises a *stub finalize*. It prints one specific `FAIL:` line (for example `FAIL: record 0 was a pending stub (606 B) and was finalized in the trim commit; the other 5 record(s) are byte-identical across the move, in order, and L2 holds`) and a `NOTE:` line, and exits 4, in place of the generic L1 and L3 failures. Exit 4 is still a FAIL, by design (see "What remains"). The `NOTE:` line explains why exit 4 is still a FAIL and states the timing rule.
- **A warning before the write.** Before it writes, the trimmer prints a warning coded `FRONTIER_PENDING_STUB` (record 0 is a pending stub now) or `FRONTIER_FINALIZE_UNCOMMITTED` (the last commit's record 0 was a pending stub and the working tree no longer holds it: the finalize is made but not committed). The warnings are advisory and refuse nothing.
- **The rule, stated.** The warnings, the proof's `NOTE:` line and `FRAMEWORK_APPARATUS.md` state the timing rule. A proof that does not recognise a stub finalize already printed a `NOTE:` line when it met the finalize pattern; this commit rewords that line to state the timing rule. The old wording had called committing a finalize together with a trim this repository's own practice; the new wording says it is not the framework's practice.

**Commit 3 (`TRIM_VERSION` 1.7.0): a second verdict for a proof already written. Addresses cause 3.** To *re-derive* a shard's proof is to build the proof that the *running trimmer* would write for that shard, from its own template, and run it. The running trimmer is the version of `methodology_trim.py` that is executing `--reverify`, as against the version recorded in the shard's original proof. `methodology_trim.py --reverify <shard>` (the shard, or its `.verify.sh`) does that, as follows. Unlike a trim, `--reverify` needs no table entry for the ledger.
- `--reverify` reads from the shard's existing proof the ledger's path (`LIVE`), the shard's path (`SHARD`), and the *record grammar*, which says how records are told apart: `RECORD_KIND` (records are dated headings or fenced blocks), `RECORD_START` (a regular expression that matches the line that begins a heading record), `FENCE_INFO` (the word after a fenced record's opening fence, such as `handoff`) and `FOOTER_MODE` (whether the ledger has a footer). When the proof has them, `--reverify` also reads `REGEN_PATTERNS` (regular expressions that find the header fields the trimmer, not the session, rewrites) and `STUB_PATTERN`.
- `--reverify` fills in a value that the existing proof lacks. A proof written before 1.6.0 has no `STUB_PATTERN`; `--reverify` uses the `stub_marker` of the ledger table's entry for the ledger's file name, or none if the table has no entry or the entry declares no `stub_marker` (the `CHANGELOG.md` entry declares none). A proof written before 1.1.2 has no `REGEN_PATTERNS`; `--reverify` uses none, so no header field is exempted. The banner says which values were filled in.
- `--reverify` prints a banner first, saying that the verdict comes from the running trimmer's logic and not from the original proof file, and a line for each value it substituted. It then runs the re-derived proof and prints the proof's own output as the verdict.
- The exit status is that of the re-derived proof (0 holds, 1 FAIL, 4 stub finalize), or 3 when no verdict can be reached: the shard is outside a git work tree, has no proof next to it, its proof is for a different shard or has a line that is not in the exact form the template writes, or the re-derived proof cannot be run to the end.

`--reverify` writes no file: it passes the re-derived proof to `bash -c`, so the shard, the original proof and git are unchanged. The original proof stays as it was, so there are two verdicts on the shard: the original proof's, whenever it is run, and the one `--reverify` prints. A proof written by this branch's trimmer and a proof re-derived by `--reverify` come from the same function (`render_verify`), so they behave alike.

**Commit 4 (`TRIM_VERSION` 1.8.0): `SESSION_NOTES.md` joins the ledger table, and the proof prints the record-0 diff. Reaches the 7 proofs Commit 2 could not.** Commit 2's recognition needs a stub marker, and a marker comes from the ledger table, so the 7 `SESSION_NOTES.md` shards in the #93 repository got none. This commit adds two things:
- **A table entry for `SESSION_NOTES.md`.** The session runner's Phase 1B writes a stub into this file and its Phase 3D overwrites the stub in place, exactly as with the `HANDOFFS.md` receipt; the seed copy of the file calls itself transient, but its own last line says session history accumulates below it, and the #93 repository holds 577 record headings. The entry's grammar is the runner's own: a record starts at `### What Session N Did` or at `### Session N-1 Handoff Evaluation (by Session N)`, and at nothing else, so the seed's `### What You Must Do` heading stays header text and a `###` sub-heading inside a session's write-up stays inside that record. The file has no footer. A record's date, used only to label a shard's span, is its `**Started:**` line (or `**Started/Completed:**`, `**Completed:**`, `**Date:**`), else the first date in the record. The entry's stub marker requires *both* Phase 1B lines, the `**Status:** Session claimed` line (which must start a line, so a mid-line quote is not one) and the `(IN PROGRESS)` tag, anywhere in the record, because the tag's line can wrap and 4 of the 7 real stubs appended text to the status line. The two-part shape is measured, not assumed: over the live notes files of 12 adopters, a finished record in 3 of them still carries the status line, and 2 of those 3 records dropped the tag, so the line alone would have called finished records stubs; all 7 of the #93 repository's real stubs match both parts, and none of the records that replaced them does. The #93 repository's own table entry uses the same record grammar; after this commit the canonical entry reads that repository's `SESSION_NOTES.md` exactly as its own entry does (42 records at its commit `82433662`, the same header text).
- **The diff of record 0.** Whenever the proof sees the finalize pattern (record 0 edited in the trim commit, for a recognised stub finalize at exit 4 and for the generic case at exit 1 alike), it prints, after its `FAIL:` and `NOTE:` lines, a unified diff of record 0 before the trim commit against the record that replaced it, headed `DIFF: record 0, ...` with the line count. This is issue #93's first suggestion. The diff is output, not a verdict: it changes no exit status, and a record other than record 0 that differs gets no diff, because that is a plain loss.

What Commit 4 does not change: a recognised stub finalize stays a FAIL at exit 4 (see "What remains"); the verdicts for the two existing ledgers (measured on the 174 frozen shards of the contributor's fork, every exit code the same under 1.7.0 and 1.8.0).

**Commit 5 (`TRIM_VERSION` 1.8.1): an abort before the proof's checks exits 3, not 1.** A proof that cannot read an artifact from git (a partial or shallow clone that lacks the trim commit's parent; a blob fetch that fails) ended in `sys.exit("verify: cannot read ...")`, which exits 1, the FAIL code, so a proof that had compared nothing read as a trim that lost something; the sweep behind this PR saw it once (exit 0 on the re-run). Every such abort now prints its reason and exits 3, the code the `--reverify` legend gives "the proof did not finish". Frozen proofs are unchanged; `--reverify` renders today's template and reads 3. Four tests on a depth-1 clone of a trimmed repository; the `trimmer-unit-tests` gate 199 → 203; the 54 proofs read the same under 1.8.1 as under 1.8.0.

## Where to read closely

`--reverify` reads values out of a proof file that belongs to the repository being checked, so the file's text is not trusted. `--reverify` places some of the values into an unquoted shell assignment and the rest into Python, in the proof that it then runs, so a value containing shell or Python code would run. The reading is therefore strict, not a loose pattern match:
- each required line must match, whole, the form the template writes;
- `REGEN_PATTERNS` and `STUB_PATTERN` are parsed as literals and never evaluated;
- paths may not be absolute or contain `..`.

The code is in `starter-kit/methodology_trim.py`. "Lift" is the code's word for reading a value out of a proof: `_LIFT_REQUIRED` lists the lines that must be present and the exact form of each, `_lift_line` finds one such line, `_lift_pattern` checks a pattern value, and `lift_grammar` does the whole reading. Four tests plant hostile text: (1) shell code in the `LIVE` line; (2) Python code in the `RECORD_START` line; (3) a Python expression in the `REGEN_PATTERNS` line, and then in the `STUB_PATTERN` line (one test, run for each line); (4) a shell command in a shard's file name. Each test has a control showing the text would run if pasted in naively, then asserts that `--reverify` refuses it and nothing runs.

The new `SESSION_NOTES.md` entry's stub marker is a regular expression of two lookaheads under the `(?ms)` flags; the comment above it in the `LEDGERS` table says what each part is for and gives the measurement. The diff is built with Python's `difflib` from the two record texts the proof already holds.

## What remains, and why the 8 stay FAILs

The authors of #93 ask for these false FAILs to stop. The original proof files do not change, so for a proof already written this PR can only add a second verdict, the one `--reverify` gives. Under that verdict, 2 of the 10 proofs pass and 8 are each recognised as a stub finalize: a specific `FAIL:` line, exit 4, and the diff of the stub against the record that replaced it. None of the 10 prints the generic failures any more.

Each of the 10 original proofs prints exactly one of three failure lines that tell the causes apart: `L2 FRONT MATTER leaked` is cause 2, `L3 record count 79 != 78` is cause 3, and `L3 1 record(s) present before the trim are MISSING` is cause 1. (The cause-1 and cause-3 proofs also print an L1 failure line, which does not tell the causes apart.) Sorting by line gives 7 proofs for cause 1, 2 for cause 2 and 1 for cause 3, which are the counts #93 gives.

| #93's cause | Failing proofs | `--reverify` result after Commit 3 | `--reverify` result after Commit 4 |
|---|---|---|---|
| 1: a trim in the same commit as a finalize | 7: one `HANDOFFS.md` shard and six `SESSION_NOTES.md` shards | the `HANDOFFS.md` shard exits 4; the six `SESSION_NOTES.md` shards exit 1 | all 7 exit 4, named, with the diff |
| 2: L2 compares by substring | 2: one `CHANGELOG.md` shard and one `HANDOFFS.md` shard | both pass (exit 0) | both pass (exit 0) |
| 3: a proof already written | 1: a `SESSION_NOTES.md` shard, written by trimmer version 1.1.2 | exit 1 | exit 4, named, with the diff |

In each of the 8, the re-derived proof reports the finalize pattern: record 0 was a stub before the trim commit, a record with the same heading or `session:` line replaced it, and no other record differs. The cause-3 proof shows the same pattern, because its trim commit overwrote the stub as well as adding a record. The pattern stays a FAIL by design, because neither the original proof nor the re-derived one can tell it from a real loss: if the edit to record 0 had also deleted part of its text, the proof would see the same pattern, record 0 changed and everything else identical. In all 8 the finished record rewrote the stub's text; apart from the identifying lines, no line of the stub survives as a whole line in the finished record, and one stub carried 23 lines of prose written into it. #93's authors judged by hand that nothing of value was lost; a proof cannot, and a proof that exited 0 here would certify a replaced stub it has not read. What the proof can do is show the edit, which is what the diff is for: in these 8 the diff runs from 30 to 176 lines, and a reader sees in seconds that the removed lines are the placeholder's and the added lines are the session's write-up.

## Summary

This PR changes `methodology_trim.py` (the trimmer), the tool that moves the oldest records out of a growing file into an archive file and writes a script, a *proof*, that re-checks that nothing was lost. Issue #93 reports 10 of 54 proofs, in one project, failing on trims that lost nothing, and traces them to three causes. This PR fixes one cause, makes another recognisable and avoidable, and adds a command, `methodology_trim.py --reverify <shard>` (a *shard* is an archive file that an earlier trim wrote), that builds a new proof for a shard from the current template and runs it, so a shard whose proof was written earlier gets a second verdict. This PR does not close issue #93: of its 10 proofs, 2 pass and 8 still fail under `--reverify`, for a reason that "What still fails" explains.

## Background

`methodology_trim.py` trims a **ledger**: a file of dated records, newest first, that grows with every session. The trimmer works only on the ledgers listed in its **ledger table**, a Python dictionary named `LEDGERS` that is written in the code of `methodology_trim.py` (there is no separate configuration file). The table has two entries: `CHANGELOG.md` (one record per action) and `HANDOFFS.md` (one record per session, called a receipt). When it trims, the trimmer refuses a file that has no table entry (exit 3). This repository is the framework's own; `bin/sync` copies `methodology_trim.py` from it into the projects that use the framework (*adopters*).

A trim moves the oldest records of a ledger into an archive file, a **shard** (in `docs/archive/`), and writes a **proof** next to it, in the same directory: `<shard>.verify.sh`. The commit that adds the shard is the **trim commit**. The trimmer writes a short header at the top of the shard; the header says which ledger the records came from and how many records the shard holds. The trimmer generates each proof from a template (`VERIFY_TEMPLATE`). The proof is a script that re-checks, from git, that the trim lost nothing: it compares the ledger as it was in the trim commit's parent (*before*) with the ledger and the shard as they are in the trim commit (*after*). The proof runs three checks:

- **L1:** every byte of the *before* ledger's records is still in the *after* ledger's records or in the shard's records.
- **L2:** the ledger's header (the text above the first record, which the trimmer calls *front matter*) and footer (the text below the last record; `HANDOFFS.md` has none) are still in the ledger, and no line of them was copied into the shard (neither into the shard's own header nor among its records). Two exceptions: the header fields that the trimmer, not the session, rewrites (such as a receipt count) may change, and header lines of 24 characters or fewer are not checked for copying.
- **L3:** each record of the *before* ledger is, unchanged and in order, either in the *after* ledger or in the shard. Records that the trim commit itself added to the ledger (a new session's records, for example) are left out of the comparison.

A proof exits 0 when the checks hold and 1 when one fails. A proof is written once, when the trim happens, and never changes afterwards (it is *frozen*). Each proof states the trimmer version that wrote it; the trimmer's version number is `TRIM_VERSION`.

## What issue #93 reports

Issue #93 reports 10 of the 54 proofs in one adopter repository, `rmsharp/nprcgenekeepr` (the *#93 repository*), failing. The authors of #93 diffed the records of all 10 by hand and found no real loss, so each is a *false FAIL*: a FAIL on a trim that lost nothing. The issue traces the 10 to three causes.

The #93 repository also trims a third ledger, `SESSION_NOTES.md` (a file with one record per session). Because the trimmer refuses a file with no table entry, the repository added a table entry for it to the `LEDGERS` table in its own copy of `methodology_trim.py`. The table in this repository's `methodology_trim.py` has no such entry.

1. **A trim in the same commit as a finalize (7 proofs).** A session starts by committing a placeholder record at the top of a ledger, the *stub*; that commit is the session's *claim*. In `HANDOFFS.md` the stub is a receipt marked `status: pending`; in `SESSION_NOTES.md` it is a record marked `(IN PROGRESS)`. The session ends by overwriting the stub in place with the finished record: the *finalize*. When a trim lands in the same commit as the finalize, the proof sees the newest record (*record 0*, which the trimmer also calls the *frontier*) change. The proof prints record 0 as `MISSING:` and prints an added record with the same identifying line (its heading, or the `session:` line of a receipt) as `added:`; that is the *finalize pattern*. The proof fails L1 and L3.
2. **L2 compares by substring (2 proofs).** L2 treated a line of the ledger's header as copied into the shard whenever the line occurred anywhere inside an archived record. A record that quoted the header line `## Size, and when to archive` in backticks, inside a longer line, therefore counted as a copy.
3. **A proof already written never gets later fixes (1 proof).** The template has been fixed since, but a proof is never regenerated. The cause-3 proof was written by trimmer version 1.1.2, whose template assumed that the trim commit adds a fixed number of records to the ledger, written into each proof as a constant (`INJECTED=0`: assume none). The trim commit also contained the session's close-out (the step that finishes a session). The close-out added one new record, an evaluation of the previous session's handoff, and overwrote the stub. The ledger and the shard together then held one record more than before the trim, 79 against 78, so L3 reported `record count 79 != 78`. Version 1.2.0 replaced the constant with a measurement of which records the trim commit added, but this proof was not regenerated.

## What this PR changes

One commit per cause, each with its own tests and its own record in `CHANGELOG.md`. The three share the proof template and its tests, so they are one change set. This PR does not close issue #93; "What still fails" says why.

**Commit 1 (`TRIM_VERSION` 1.5.1): L2 compares whole lines. Fixes cause 2.** L2 now tests whether a line of the ledger's header equals a whole line of the shard's header or of its records, instead of occurring anywhere inside them. The 24-character exception stays.

**Commit 2 (`TRIM_VERSION` 1.6.0): a stub finalize is recognised and warned about. Addresses cause 1.** The *timing rule* avoids the problem: trim while record 0 is complete, that is, before the claim or after the finalize is committed, never in the same commit as the finalize. This commit adds three things:
- **A proof that recognises a stub finalize.** An entry in the ledger table can declare a `stub_marker`: a regular expression that must match a whole line and identifies a pending stub (for `HANDOFFS.md`, the line `status: pending`), so a receipt that merely quotes the marker inside a longer line is not taken for a stub. A proof is a self-contained script that does not import the trimmer, so it cannot look the marker up; it contains a copy as `STUB_PATTERN`. When record 0 matched the stub marker before the trim, no longer matches it after, L2 holds, and every other record is unchanged and in order, the proof recognises a *stub finalize*. It prints one specific `FAIL:` line (for example `FAIL: record 0 was a pending stub (606 B) and was finalized in the trim commit; the other 5 record(s) are byte-identical across the move, in order, and L2 holds`) and a `NOTE:` line, and exits 4, in place of the generic L1 and L3 failures. Exit 4 is still a FAIL, by design (see "What still fails"). The `NOTE:` line explains why exit 4 is still a FAIL and states the timing rule.
- **A warning before the write.** Before it writes, the trimmer prints a warning coded `FRONTIER_PENDING_STUB` (record 0 is a pending stub now) or `FRONTIER_FINALIZE_UNCOMMITTED` (the last commit's record 0 was a pending stub and the working tree no longer holds it: the finalize is made but not committed). The warnings are advisory and refuse nothing.
- **The rule, stated.** The warnings, the proof's `NOTE:` line and `FRAMEWORK_APPARATUS.md` state the timing rule. A proof that does not recognise a stub finalize already printed a `NOTE:` line when it met the finalize pattern; this commit rewords that line to state the timing rule. The old wording had called committing a finalize together with a trim this repository's own practice; the new wording says it is not the framework's practice.

**Commit 3 (`TRIM_VERSION` 1.7.0): a second verdict for a proof already written. Addresses cause 3.** To *re-derive* a shard's proof is to build the proof that the *running trimmer* would write for that shard, from its own template, and run it. The running trimmer is the version of `methodology_trim.py` that is executing `--reverify`, as against the version recorded in the shard's original proof. `methodology_trim.py --reverify <shard>` (the shard, or its `.verify.sh`) does that, as follows. Unlike a trim, `--reverify` needs no table entry for the ledger.
- `--reverify` reads from the shard's existing proof the ledger's path (`LIVE`), the shard's path (`SHARD`), and the *record grammar*, which says how records are told apart: `RECORD_KIND` (records are dated headings or fenced blocks), `RECORD_START` (a regular expression that matches the line that begins a heading record), `FENCE_INFO` (the word after a fenced record's opening fence, such as `handoff`) and `FOOTER_MODE` (whether the ledger has a footer). When the proof has them, `--reverify` also reads `REGEN_PATTERNS` (regular expressions that find the header fields the trimmer, not the session, rewrites) and `STUB_PATTERN`.
- `--reverify` fills in a value that the existing proof lacks. A proof written before 1.6.0 has no `STUB_PATTERN`; `--reverify` uses the `stub_marker` of the ledger table's entry for the ledger's file name, or none if the table has no entry or the entry declares no `stub_marker` (the `CHANGELOG.md` entry declares none). A proof written before 1.1.2 has no `REGEN_PATTERNS`; `--reverify` uses none, so no header field is exempted. The banner says which values were filled in.
- `--reverify` prints a banner first, saying that the verdict comes from the running trimmer's logic and not from the original proof file, and a line for each value it substituted. It then runs the re-derived proof and prints the proof's own output as the verdict.
- The exit status is that of the re-derived proof (0 holds, 1 FAIL, 4 stub finalize), or 3 when no verdict can be reached: the shard is outside a git work tree, has no proof next to it, its proof is for a different shard or has a line that is not in the exact form the template writes, or the re-derived proof cannot be run to the end.

`--reverify` writes no file: it passes the re-derived proof to `bash -c`, so the shard, the original proof and git are unchanged. The original proof stays as it was, so there are two verdicts on the shard: the original proof's, whenever it is run, and the one `--reverify` prints. A proof written by this branch's trimmer and a proof re-derived by `--reverify` come from the same function (`render_verify`), so they behave alike.

## Where to read closely

`--reverify` reads values out of a proof file that belongs to the repository being checked, so the file's text is not trusted. `--reverify` places some of the values into an unquoted shell assignment and the rest into Python, in the proof that it then runs, so a value containing shell or Python code would run. The reading is therefore strict, not a loose pattern match:
- each required line must match, whole, the form the template writes;
- `REGEN_PATTERNS` and `STUB_PATTERN` are parsed as literals and never evaluated;
- paths may not be absolute or contain `..`.

The code is in `starter-kit/methodology_trim.py`. "Lift" is the code's word for reading a value out of a proof: `_LIFT_REQUIRED` lists the lines that must be present and the exact form of each, `_lift_line` finds one such line, `_lift_pattern` checks a pattern value, and `lift_grammar` does the whole reading. Four tests plant hostile text: (1) shell code in the `LIVE` line; (2) Python code in the `RECORD_START` line; (3) a Python expression in the `REGEN_PATTERNS` line, and then in the `STUB_PATTERN` line (one test, run for each line); (4) a shell command in a shard's file name. Each test has a control showing the text would run if pasted in naively, then asserts that `--reverify` refuses it and nothing runs.

## What still fails

The authors of #93 ask for these false FAILs to stop. The original proof files do not change, so for a proof already written this PR can only add a second verdict, the one `--reverify` gives. Under that verdict, 2 of the 10 proofs pass and 8 fail. That is why this PR does not close issue #93.

Each of the 10 original proofs prints exactly one of three failure lines that tell the causes apart: `L2 FRONT MATTER leaked` is cause 2, `L3 record count 79 != 78` is cause 3, and `L3 1 record(s) present before the trim are MISSING` is cause 1. (The cause-1 and cause-3 proofs also print an L1 failure line, which does not tell the causes apart.) Sorting by line gives 7 proofs for cause 1, 2 for cause 2 and 1 for cause 3, which are the counts #93 gives. The `--reverify` results below are this branch's, so they used this branch's ledger table (two entries), not the #93 repository's own (three).

| #93's cause | Failing proofs | `--reverify` result |
|---|---|---|
| 1: a trim in the same commit as a finalize | 7: one `HANDOFFS.md` shard and six `SESSION_NOTES.md` shards | the `HANDOFFS.md` shard exits 4; the six `SESSION_NOTES.md` shards exit 1 |
| 2: L2 compares by substring | 2: one `CHANGELOG.md` shard and one `HANDOFFS.md` shard | both pass (exit 0) |
| 3: a proof already written | 1: a `SESSION_NOTES.md` shard, written by trimmer version 1.1.2 | exit 1 |

In each of the 8 proofs that still fail, the re-derived proof reports the finalize pattern: it prints `MISSING:` for record 0 and `added:` for a record with the same identifying line as record 0, and no other record is missing. A finalize committed together with a trim leaves this pattern. The cause-3 proof shows it too: its trim commit overwrote the stub and added a new record. The pattern stays a FAIL by design, because neither the original proof nor the re-derived one can tell it from a real loss: if the edit to record 0 had also deleted part of its text, the proof would see the same pattern, record 0 changed and everything else identical. #93's authors checked by hand that these trims lost nothing, which the proof cannot establish.

The 8 differ in whether the re-derived proof recognises the pattern as a stub finalize, which needs a stub marker:
- The `HANDOFFS.md` shard is recognised. `HANDOFFS.md` has a stub marker in the ledger table, so `--reverify` prints the specific `FAIL:` line and exits 4.
- The seven `SESSION_NOTES.md` shards (the six in cause 1 and the one in cause 3) are not recognised. `SESSION_NOTES.md` has no entry in this branch's ledger table, so `--reverify` has no stub marker for it. The re-derived proof prints the generic L1 and L3 failures, exit 1, followed by the `NOTE:` line that describes the pattern in words and says to diff record 0 by hand. For the cause-3 shard, the record-count error (`79 != 78`) no longer appears; the generic failures and that note appear instead.

## Three questions this pull request leaves open

All three are about `SESSION_NOTES.md`. The first two come from your first review of #94, which said: "A 123,325 B notes file fails `context_budget` while `--check` says no trim is due" and "If only some headings match (e.g. lowercase `did`), a trim can't get the file under the limit and says nothing about why." The third turned up when I ran the first commit over real notes files. Questions 1 and 2 are reproduced on throwaway repositories built to the shape described, not on a real project's file; question 3 is a real project's file.

### 1. When should `--check` say a notes file is due for a trim?

Today the trimmer's `--check` says a root `SESSION_NOTES.md` is due only at 196,608 B, the size it uses for root `CHANGELOG.md` and `HANDOFFS.md` (`is_root_class_a`, the function you pointed at in your review). But the runner has every session read `SESSION_NOTES.md` at Phase 0, and the seed `.context-budget.json` that `bin/sync` installs classes it `read-mandated` and caps it at 400 lines, 120,000 B and 25,000 tokens. So a notes file between 120,000 B and 196,608 B is over its budget and, to the trimmer, not due.

Reproduced with a throwaway repository holding a notes file of 123,325 B (your figure): `context_budget.py --status` exits 2, over its byte, line and token ceilings, while `methodology_trim.py --check` exits 0 and prints `trigger does not fire`.

- **(a)** Take this file out of that class. `--check` would then use the 56,750 B "one-read cap" (the size past which a whole-file read comes back truncated) that nested and unclassified ledgers get, so it would fire before the budget's 120,000 B and never be silent while `context_budget.py` is red. The cost: it would call a notes file due at 56,750 B, well inside its own budget.
- **(b)** Keep 196,608 B, and say in `FRAMEWORK_APPARATUS.md` and in the table entry's comment that for this file the budget trips first and `--check` is not the test of whether the file is over budget.

Which do you prefer?

### 2. Should the trimmer say so when a heading does not match?

The entry recognizes a record by exactly the two heading forms in commit 1. Everything above the first matching heading counts as front matter, however long it is. When no heading matches at all the trimmer does not stay silent: with dated headings it refuses (`GRAMMAR_MISMATCH`, exit 3), with undated ones it reports zero records. The gap is the partial match.

Reproduced with a throwaway notes file of 160 records and 249,840 B whose newest 135 records say `### What Session N did` (lowercase) and whose older 25 say `Did`. The trimmer reads 25 records and treats the 135 newer ones as a very large front matter. The dry run (no `--cut`, so the trimmer chooses) reports `would archive 24 of 25 record(s)` and `live 249,840 B → 213,031 B`: it archives all but the newest of the 25 it recognized, leaves the file far above its limits, and says nothing about the 135 sections it did not read.

- **(a)** A finding whenever the front matter contains a heading-shaped line (`### ... Session <number> ...`), so the dry run and the write say what they did not read. This covers any variant of the heading.
- **(b)** Match `Did` case-insensitively. This fixes the case above and no other, and it combines with (a).

Which do you prefer?

### 3. A `---` line inside the oldest record the trim keeps

The entry declares no footer, so nothing after the last record is a separate zone. A standalone `---` line that has more text after it inside the oldest record the trim keeps (the last record in the file) is therefore text the entry's grammar has no name for.

One real project's notes file hit it. It has four records. `--cut 3` (keep the newest three) would keep `### What Session 205 Did` as the last record, and that record has a `---` at line 31 followed by its close-out block. The trimmer plans the trim, finds that the text it would write does not parse under its own declared grammar, and the dry run ends `ARTIFACT_UNPARSEABLE` ("the text this run would write does not parse under its own declared grammar"). That message names neither the line nor the cause. Removing that one line lets the same dry run plan the trim, and so does `--cut 2`, which keeps a last record whose rule is followed by nothing. It is the same at 1.9.0 (commit 1), so it predates commits 2 and 3. It is a refusal, not a loss.

- **(a)** A footer mode for notes files that counts a trailing rule as part of the last record.
- **(b)** Keep the refusal, and make the finding name the line and say what to do.

Which do you prefer?

### Underneath: is `SESSION_NOTES.md` transient, or does it accumulate?

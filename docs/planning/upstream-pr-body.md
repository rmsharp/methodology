## What the change does

- **Paths.** `bin/sync` writes a project that keeps the current layout (called `legacy` in the tools' `--layout` options) the same paths it writes today (measured below). `bin/sync` and `bin/check-links` take `--layout` (for `bin/sync`, `auto` is the default: it keeps the layout a project has, and gives an empty project the current layout); `bin/status` and every other tool read either layout. The manifest has a second table, `NEW_LAYOUT`, giving each file's place under `methodology/`; it is plain data, so `bin/sync --source github` (which clones the framework repository) can read it without running it.
- **No tool guesses where the files are.** `tools/layout_resolver.py` is a short block of code that decides a project's layout from where an anchor file sits. The default anchor is `SESSION_RUNNER.md`: at the root, the current layout; under `methodology/`, the new one; in both places, the tool refuses and names both. A tool that reads a ledger anchors on that ledger instead, and the ratchet and the budget tool on their configuration file, so a project that moved only the framework's files (`--tier 1`, below) is read correctly. For a file other than the anchor that exists in both places (for example a project's own product `CHANGELOG.md`), the tool reads the copy under `methodology/` as the framework's and leaves the other alone, but only when the runner is under `methodology/` and not at the root; otherwise it refuses. The block is copied into 10 tools and into the dashboard's identical copy, because the four tools a project receives (`methodology_dashboard.py`, `methodology_trim.py`, `context_budget.py`, `quality_ratchet.py`) are single files that import only the standard library; the six tools that stay in this repository carry the same block, so one test covers all 11. `python3 tools/test_layout_resolver.py` fails until all 11 copies equal `tools/layout_resolver.py`.
- **Moving a project.** `bin/migrate-layout` makes no change unless given `--apply`. `--tier 1` moves the framework's files, `--tier 2` the project's own state (its seed files, the files the tools generate, the archive shards the trimmer wrote, and the project-owned PROJECT_LEARNINGS.md that `BOOTSTRAP.md` names), `all` (the default) both.
  - *It refuses, before writing anything,* a tree that is not a git repository with a commit; has uncommitted changes; is half-migrated (a runner at the root and another under `methodology/`); already holds a destination file; keeps its framework files out of git (its `.gitignore` lists them); is not current with what `bin/sync` would write; or has a file to rewrite that it cannot rewrite safely (for example, a ledger with a code fence that never closes).
  - *An apply is one commit.* It moves the files, rewrites the moved paths in `CLAUDE.md`, in anchored `.gitignore` entries and in `.context-budget.json` and `.quality-gates.json`, and adds a ledger entry. Every move must remain a rename at 90% similarity or better, so that `git log --follow` still reaches the history; a ledger too small for that fails (a project with a very short ledger must add entries first), and the apply is rolled back (exit 3), as is any step that fails before the commit. The report names `git revert <commit>` as the way back.
  - *It checks itself.* Before and after the commit it runs read-only checks (`bin/status`, the two ledger checkers, `bin/check-links`, every archive shard's proof, and how far `git log --follow` reaches). If a result differs afterwards, it exits 4 and keeps the commit (`--skip-checks` turns the checks off).
  - Like `bin/sync` and `bin/status`, it is not in `bin/_manifest.py`; a project runs it from a checkout of this repository. Its own suite of 280 tests (separate from `bin/tests.sh`) takes about 6 minutes, so the two gates that run it each set `timeout_seconds` to 3600.

## Known gaps

These came from the 12 projects and are open:

- A sync refuses a project's edited framework file by name but does not say which published version is nearest or how many lines differ, and `--force` then drops the edit (upstream's `bin/sync` does the same).
- With only the framework's files moved (`--tier 1`), the dashboard writes a second history file, `dashboard_history.jsonl`, under `methodology/` while the one at the root stays, unused.
- On a ledger in the old format (no month headings), the migration appends its entry at the end, out of order; `bin/check-ledger` fails on such a ledger before and after.
- For the hook that `context_budget.py install-hook` writes, the migration warns that it "will refuse the migration commit". In fact the hook does not refuse it.
- An earlier copy of the ledger pre-commit hook of `SAFEGUARDS.md` keeps looking for the ledger at the root, so once the ledger moves it passes a commit with no ledger entry, without saying so. The migration reports such a hook and leaves it. The hook in this branch (`.githooks/pre-commit`) follows the ledger.
- A project's own tests or scripts that read a moved file by name can break. The migration lists the other files whose text mentions a moved name; the list is an upper bound, not the set that breaks.
